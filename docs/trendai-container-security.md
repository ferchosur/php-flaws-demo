# Preparing a TrendAI Vision One Container Security evaluation

**Status checked:** 2026-10-24. The namespace `trendmicro-system` is reserved in the existing Kind cluster. No TrendAI chart or sensor has been installed; no tenant bootstrap token, console access, or account/license details were available.

## Support and installation gate

The installed Kubernetes API reports `v1.31.2`. Kubernetes 1.31 reached upstream end of life on 2025-11-11. TrendAI's Kubernetes system requirements say Container Security supports Kubernetes versions until their official EOL. Therefore this cluster is outside that support window on the date of this assessment. The getting-started matrix includes self-managed Kubernetes, but no specific certification for Kind on Docker under WSL2 was found. The local node also runs inside a Docker container rather than on a conventional host.

The active chart release at the check date was **3.5.5** (released 2026-10-14). Helm 3.21.3 is installed and satisfies the chart's Helm 3+ requirement. The chart's runtime sensor needs node-level runtime visibility and host/runtime integration; the chart also documents a privileged Pod Security Standard namespace requirement when Runtime Security is enabled. Installing it here would grant elevated, host-adjacent access on an out-of-support Kubernetes version. Per the project constraints, this was not attempted.

Observed node capacity (14 CPU, ~15.3 GiB allocatable) exceeds the vendor's published runtime-security incremental requests (0.2 CPU and 768 MiB per node). Capacity does not remedy the Kubernetes EOL/support issue. The Kind node had no taint, and containerd 1.7.18 was present inside the Kind node container.

Container Security documentation requires NetworkPolicy support for its isolation mitigation. The current Kind CNI is `kindest/kindnetd:v20241023-a345ebe4`. With the lab policies applied, the verification's benign C-to-B health request was blocked (PASS for that tested cross-namespace path). This confirms the sampled path is blocked; it is not a complete audit of every ingress/egress route or evidence of TrendAI detection. No CNI replacement was performed.

## Version pin and credential handling

The public chart release list was checked and 3.5.5 was the latest release at the time. On a supported Kubernetes cluster, use the pinned version rather than an unversioned chart. Official chart setup requires a bootstrap token from the Vision One Container Security console; the documented token expires after 24 hours. Use a Kubernetes Secret and the chart's `useExistingSecrets.containerSecurityAuth` option. Never put the token in this repository, a values file, command history, or diagnostics.

Feature overrides are prepared in `labs/trendai-container-security/values.example.yaml`. It enables Runtime Security and vulnerability scanning only. Malware and secret scanning remain disabled until separately authorized and scoped. To install on a supported cluster after confirming vendor support for that environment and obtaining a short-lived token:

~~~bash
kubectl create secret generic trendmicro-container-security-bootstrap-token \\
  --namespace trendmicro-system \\
  --from-file=bootstrap.token=/secure/path/bootstrap.token
helm install trendmicro \\
  --namespace trendmicro-system \\
  --version 3.5.5 \\
  --values labs/trendai-container-security/values.example.yaml \\
  oci://public.ecr.aws/trendmicro/container-security/trendmicro-container-security
~~~

Those commands are a documented procedure, not executed commands. A supported test cluster must have vendor-approved network access to the Vision One endpoint and image registry, available RBAC privileges for the chart, and the runtime security node components scheduled successfully. Review the chart's host paths, capabilities, and Pod Security requirements for the selected feature set before installation.

## Evaluation sequence

1. Connect the supported cluster to the tenant and create a test policy in log-only mode.
2. Capture the image inventory for A, B, and C separately by digest/imageID, plus package/version evidence and scan timestamp. B and C are distinct vulnerable-only local images in this Kind setup; use an approved isolated registry if the feature cannot scan locally loaded artifacts.
3. Capture workload configuration findings separately: user, capabilities, mounts, root filesystem, Service exposure, namespace and NetworkPolicy enforcement.
4. Record findings independently for B and C after scanner ingestion. A finding or its absence applies only to that image digest and scan time; it does not prove exploitability.
5. Plan remediation scans in a separate future phase. This lab deploys no corrected target.
6. Treat runtime threats as a separate evaluation. No exploit, malicious event, arbitrary command, or PoC is generated by this lab. Runtime detection remains NOT TESTED unless an approved benign vendor test is selected and documented.
