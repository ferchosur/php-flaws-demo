# TrendAI Vision One validation procedure

**Status:** procedure prepared; no Vision One tenant, registry connector, or Console access was available in this work. No findings or threat detections are claimed.

## Separate the questions

| Signal | What it can establish | What it does not establish |
|---|---|---|
| Image vulnerability/SBOM scan | Whether the scanned image packages match vulnerability intelligence, subject to scanner coverage and scan freshness | That the vulnerability was exploited |
| Container configuration/posture | Whether the observed Kubernetes workload violates enabled policy checks (for example identity, privileges, mounts, or exposure) | PHP runtime exploitability |
| Runtime threat detection | Whether enabled runtime sensors/rules reported observed behavior | That a specific CVE caused the behavior |
| Exploitation evidence | A reproducible exploit result or independently validated incident evidence | Not collected here; no exploit or malicious event is generated |

TrendAI documentation describes Container Security inventory and vulnerability findings for connected Kubernetes clusters, plus separate Runtime Security and Runtime Malware findings. Feature availability depends on the tenant, licensing, cluster support, protection policy, and deployed components. A local Kind cluster may not satisfy the product's operational resource requirements; confirm support before installing a sensor. No agent or policy was installed by this repository change.

## Vulnerable-image inventory

1. Record UTC time, Vision One tenant/region, cluster integration, assigned policy, scanner version, and enabled features.
2. Record image reference and digest from scripts/inventory.sh. For A, capture the Kind pod's imageID; for B and C, capture the distinct local image IDs and immutable PHP base image digests in their respective Compose files.
3. Verify the exact image appears in the product inventory. If local images are not ingested, do not push a vulnerable image to a shared or production registry. Use an approved isolated test registry and a dedicated policy if tenant-side scanning requires registry access.
4. Export or screenshot findings for A and for each vulnerable PHP 8.4.26 image in B and C. Include image digest, scanner timestamp, package name/version/evidence, and finding state. If no result appears, record NOT OBSERVED rather than “clean.”
5. Record configuration findings independently from image vulnerability findings. In particular, record the actual observed namespace, deployment, service exposure, runtime user, capabilities, read-only root filesystem, mounts, and egress policy.

Remediation and before/after comparison are deferred to a later phase. No corrected runtime is deployed here.

## Runtime and posture validation

- Review deployment/continuous configuration findings separately from runtime events.
- No malicious behavior, exploit payload, shell, or suspicious child-process simulation is generated by the automated checks.
- Runtime threat detection remains NOT TESTED. If a runtime-rule test is required, select a vendor-provided benign simulation or a test explicitly approved by the tenant owner and TrendAI support; record the rule, expected signal, and cleanup before running it.
- Do not interpret absence of an event as evidence that a sensor detects this CVE.

## Evidence record

For every observation save: UTC timestamp, environment, cluster/namespace, workload, image reference, digest, PHP version/SAPI, product feature and policy, scan/event ID, finding name/status, console export or screenshot, and operator. Redact tenant identifiers or unrelated assets before sharing evidence. scripts/collect-diagnostics.sh stores local diagnostics under a private umask; it does not collect Vision One credentials or console data.
